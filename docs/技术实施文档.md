## 1 项目概述

### 1.1 项目名称

基于 Python 的演唱会数据分析与可视化系统设计与实现。

### 1.2 项目目标

系统面向演唱会公开信息整理、分析和查询服务，使用 Python 采集公开页面中的演唱会信息和评论信息，对数据进行清洗、去重、字段统一和格式转换，将结果保存到 CSV 和 MySQL 中；再对评论进行中文分词、词频统计、关键词提取和 SnowNLP 情感倾向分析，最后使用 Flask 和 ECharts 在网页中提供数据看板、地域地图、时间趋势、场次日历、票价分析、评论主题、艺人对比、规则推荐和基础后台治理功能。

### 1.3 设计原则

1. 以开题报告中的技术路线为准，不为了复杂而增加无关技术。
2. 先保证数据采集、清洗、分析和展示主流程能够运行，再完善页面细节。
3. 只处理公开、可访问、无需登录的数据，不绕过验证码、登录限制和反爬措施。
4. 保留原始数据和清洗后的数据，确保项目处理过程可以复查。
5. 不把尚未得到的实验结果写成既成事实。

## 3 功能需求

### 3.1 演唱会信息采集

采集字段包括：

- 明星名称
- 演唱会名称
- 城市
- 场馆
- 演出时间
- 原始票价文本
- 最低票价
- 最高票价
- 售票状态
- 来源页面地址
- 采集时间

首版可以先选择一位歌手进行验证，歌手名称通过配置项保存，后续可以扩展为多位歌手。具体来源以实际能够公开访问并允许记录的页面为准，不能为了完成数量而强行抓取动态页面。

### 3.2 评论信息采集

评论字段包括：

- 评论内容
- 评论时间
- 点赞数
- 用户地区
- 评论来源页面
- 采集时间

用户地区并非所有公开页面都会提供，采集不到时保存为空，不用其他字段推测地区。

### 3.3 数据清洗

清洗模块完成以下任务：

1. 去除首尾空格、HTML 标签和明显无意义字符。
2. 统一日期格式，例如统一为 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:MM:SS`。
3. 统一城市名称和售票状态的文字表达。
4. 从原始票价文本中解析数字，得到最低票价和最高票价。
5. 对缺失字段进行标记；关键字段缺失时将记录放入异常数据文件。
6. 根据来源编号或“演唱会名称 + 城市 + 演出时间 + 场馆”删除重复记录。
7. 对评论内容去重，但保留原始评论文本以便复查。

### 3.4 数据分析

系统完成以下基础分析，并在扩展阶段增加多维聚合：

- 不同城市的演唱会场次统计。
- 不同票价区间的数量统计。
- 不同时间段的演唱会场次和评论数量变化。
- 用户地区分布统计（仅统计实际获得的地区字段）。
- 评论高频词和关键词统计。
- 评论情感倾向分布。
- 不同情感类别下的关键词对比。
- 城市节点、场次数量和评论热度的地域分布。
- 按月或按周比较演出场次、评论量和平均情绪分数。
- 票档数量、城市价格差异和价格—评论热度关系。
- 现场体验、舞台音响、交通场馆、票价购票和服务组织等评论主题统计。
- 不同艺人的场次、覆盖城市、平均最低票价、评论量和情绪均值对比。

评论主题使用可解释的关键词和规则匹配完成；地图坐标只使用可靠的城市级公开信息；当样本不足或只有单一艺人时，页面明确显示样本限制。本项目不进行票房预测和复杂推荐算法，只实现基于筛选条件和基础热度指标的规则型推荐。分析结论使用“从样本数据中观察到”一类的谨慎表述。

### 3.5 可视化展示

页面至少包含以下内容：

1. 演唱会信息列表和场次详情入口。
2. 城市分布柱状图和城市级地域地图。
3. 票价区间统计图、城市价格对比图和价格—热度散点图。
4. 按月或按周展示演出场次、评论数量和情绪均值的趋势图。
5. 场次日历，按日期查看演唱会详情。
6. 粉丝地区分布图或排名图。
7. 评论关键词词云图和评论主题分布图。
8. 情感倾向饼图以及主题—情绪交叉分析。
9. 艺人对比图，展示场次、城市覆盖、票价和评论热度。
10. 按艺人、城市、售票状态、票价和时间范围进行联动筛选。
11. 收藏、两到三场演唱会对比、偏好设置和带理由的规则推荐。
12. 无数据、样本不足和坐标缺失时显示明确状态，不显示误导性空图。
### 3.6 登录与管理后台

系统设置一个管理员账号，管理员登录后进入管理后台，普通用户可以直接浏览分析看板。后台分为基础操作和数据治理操作：

- 管理员登录、退出和会话校验。
- 导入演唱会或评论 CSV 快照。
- 导入前预览文件字段、记录数和示例行。
- 检查关键字段、日期、票价、状态和评论内容，输出异常原因。
- 检测重复记录，区分新增、重复和异常数据。
- 查看导入批次、成功条数、重复条数和异常条数。
- 手动触发清洗、评论分析和统计结果更新。
- 查看数据采集、导入、清洗和分析任务的运行状态与详情。
- 导出规范化演唱会数据 CSV，保留来源地址和采集时间。
- 修改或删除明显错误的演唱会基础信息，不允许管理员修改来源记录和分析结果的历史依据。

不提供公开注册和复杂的角色权限管理。管理员密码使用哈希保存，不能在代码中明文保存。

### 3.7 规则型推荐功能

推荐功能不使用复杂机器学习模型，采用简单的规则排序。用户可以选择城市、价格范围、演出时间和售票状态，系统从 `concert_info` 中筛选候选演唱会，再结合评论数量、点赞数和售票状态计算简单推荐分数，返回推荐列表。

推荐结果仅表示“符合当前筛选条件且热度较高的演唱会”，不表示用户一定会喜欢，也不进行个性化画像分析。推荐规则和权重在配置文件中保存，便于修改和测试。

扩展阶段允许用户在页面中填写城市、预算、售票状态和艺人偏好，规则函数只把这些偏好作为筛选条件和排序加分项，并为每条结果返回可解释的推荐理由。偏好和收藏数据只保存在当前浏览器，不建立公开用户账号，也不将推荐分数解释为概率或预测准确率。
### 3.8 综合扩展版功能

为避免系统停留在“基础列表加少量图表”的阶段，在不改变开题报告技术路线的前提下，系统按两个阶段扩展。第一阶段加强数据分析和后台数据治理，第二阶段增加不依赖公开注册的轻量用户交互。所有扩展仍使用现有的 Flask、SQLAlchemy、CSV、Python 和 ECharts 技术，不引入新的复杂平台。

#### 3.8.1 数据分析中心

数据分析中心围绕“地域、时间、票价、评论和艺人”五个维度组织页面：

- **地域地图**：为已知城市配置经纬度，在 ECharts 中以散点或气泡方式展示城市节点、场次数量和评论热度；没有可靠坐标的场馆不进行猜测，只保留城市统计。
- **时间趋势**：按月或按周统计演唱会场次、评论数量和平均情绪分数，支持与当前城市、艺人、售票状态和价格筛选联动。
- **场次日历**：按照演出日期展示场次密度，点击日期后显示当天的演唱会名称、场馆、票价和售票状态。
- **票价分析**：展示票价区间、各城市最低价和最高价、票档数量、价格与评论热度的关系，并提供“价格—热度”二维比较，不将其表述为票房预测。
- **评论主题**：使用关键词集合和规则匹配，将评论归入现场体验、舞台音响、交通场馆、票价购票、服务组织等主题，再统计各主题的评论数量、点赞数和情绪分布。主题识别属于规则型探索，不宣称主题模型准确率。
- **艺人对比**：在存在多位艺人数据时，对比场次数量、覆盖城市、平均最低票价、评论数量、点赞总数和平均情绪；只有一位艺人时显示样本不足提示，不伪造对比结果。

#### 3.8.2 Redis 缓存与性能优化

十万级数据规模下，若每次请求都重新加载评论并执行分词、情感与聚合统计，页面打开需要数秒甚至超时。为此引入 **Redis 缓存层**（`app/cache.py`）：

- **缓存对象**：`/api/overview`、`/api/analytics/all`（一次返回全部 14 组分析）、各单接口、`/api/recommendations`。
- **批量接口**：前端只发 `overview` + `analytics/all` 两个请求；`analytics/all` 在后端共享同一次「场次+评论采样」查询上下文，避免 14 个并发请求各自重复聚合。冷启动 14 并发 30s+ 超时 → 2 请求 3.7s 打开；缓存命中 16ms。
- **缓存键**：接口名 + 筛选参数（艺人、城市、状态、日期区间、价格区间）的 JSON 摘要，筛选变化时自动生成新键，互不污染。
- **过期策略**：分析接口 300 秒，概览和推荐 120 秒；管理后台执行导入、修改、删除、重跑分析后主动清空全部 `pulse:*` 缓存键。
- **降级策略**：Redis 不可用或连接超时时自动回到无缓存逻辑（fail-open），不影响功能；测试环境跳过缓存保证断言确定性。
- **实测效果**：冷缓存时 overview 约 1.6-3.7 秒、`analytics/all` 约 2.5 秒（两请求并发）；Redis 命中后 7-16 毫秒，首页秒开。
- **连接池调优**：十四项分析全部走数据库，若仍按 QueuePool 默认 5+10 连接，14 个并发请求会互相排队等待超时。将 `SQLALCHEMY_ENGINE_OPTIONS` 放宽为 `pool_size=20 / max_overflow=40 / pool_timeout=60`（SQLite 场景连接即用即还，放宽队列即可）。
- **单进程运行**：`run.py` 由 `debug=True` 改为 `debug=False`，关闭 Flask reloader 父子双进程，避免双实例同时持有 SQLite 锁造成连接池排队超时。
- **分析规模控制**：评论统计基于单次最多 3000 条的均匀采样（10 万评论中抽取），情感分在导入时持久化、分析时只补缺失值，避免每次请求对全量评论重复执行 SnowNLP。

#### 3.8.3 扩展分析面板

在原有九项分析基础上新增五个面板，分析中心升级为**十四项分析**：

1. **数据来源统计（07）**：按 `source_type` 区分爬虫采集与公开数据集，展示各来源的场次、艺人、城市覆盖，回应答辩复查需求。
2. **城市票价对比（08）**：基于票价分析中的各城市最低价均值，横向比较不同城市的入场门槛。
3. **互动热度榜（09）**：按演唱会关联评论的点赞总数排序，展示讨论度最高的场次。
4. **艺人热度榜（06 升级）**：新增综合热度指标（场次×3 + 评论×2 + 点赞折算），后端排序后返回 Top10，替代原先按场次排序的全量艺人列表。
5. **评论情感分布（10）**：按情感分 -1~1 五档统计评论占比（消极/偏消极/中性/偏积极/积极），直观展示全体观众对演唱会的整体情绪倾向。
6. **场次星期分布（11）**：统计演唱会落在周一至周日的场次数，日常“演唱会扎堆周末”的市场规律一目了然。
7. **售票状态占比（12）**：按售票中/即将开售/已售罄/待定等状态聚合场次数，形成环形占比图。
8. **评论平台构成（13）**：按评论区来源 URL 域名识别平台（大麦网/网易云音乐/B站），使用全量 SQL 聚合不受抽样上限影响，论文可精确引用三渠道评论量。
9. **热门场馆 Top（14）**：按承办演唱会场次数统计场馆排行，揭示各城市主要演出场馆的使用热度。

#### 3.8.4 后台数据治理与内容管理

管理后台采用**五个功能分区**（Tab 导航），从“上传文件和触发任务”扩展为完整的后台治理系统：

1. **仪表盘**：演唱会、评论、艺人、城市总量卡片，近 7 日场次趋势图，数据来源构成饼图，以及运行任务记录（`/admin/api/stats`）。
2. **演唱会管理**：分页表格（每页 20 条），支持艺人、城市、售票状态、关键字筛选，行内编辑名称、删除单条、勾选批量删除（级联删除关联评论），全部操作带二次确认（`/admin/api/concerts`、`/admin/api/concerts/summary`、批量删除接口）。
3. **评论管理**：评论分页表格，按评论内容关键字、艺人筛选，展示点赞、地区、情感分，支持逐条删除（`/admin/api/comments`、`/admin/api/comments/<id>`）。
4. **导入导出**：CSV 导入（带预览校验报告）、演唱会 CSV 导出、评论 CSV 导出（含情感分）。
5. **系统运维**：一键重建评论分析、清空 Redis 分析缓存（`/admin/api/cache/clear`）、系统环境信息。

管理后台从“上传文件和触发任务”扩展为可检查、可追踪的数据治理入口：

- CSV 导入前预览文件名、字段名、数据条数和前五行示例。
- 校验关键字段是否缺失，检查日期格式、价格格式、售票状态和评论内容长度。
- 根据演唱会名称、城市、演出时间和场馆检测重复记录，并分别统计新增、重复和异常数量。
- 对最低票价高于最高票价、价格为空、日期无法解析和未知售票状态等情况给出异常提示，不擅自填入猜测值。
- 导入完成后生成导入报告，记录输入条数、成功条数、重复条数、异常条数和错误原因摘要。
- 运行记录增加任务详情查看，能够区分导入任务、清洗任务、评论分析任务和统计刷新任务。
- 提供规范化演唱会数据 CSV 导出，导出的文件包含来源地址和采集时间，便于检查和提交验收材料。
- 提供最小化内容管理：管理员可以修改演唱会名称、场馆、时间、票价文本和售票状态，也可以删除明显错误的演唱会记录；不提供复杂角色权限和批量危险操作。

#### 3.8.5 轻量用户服务功能

第二阶段不增加公开注册和复杂用户表，普通用户的临时操作保存在浏览器 `localStorage` 中：

- **收藏**：用户收藏感兴趣的演唱会，页面显示收藏数量和收藏列表。
- **演唱会对比**：选择两到三场演唱会，比较城市、时间、场馆、最低票价、最高票价、评论量、点赞量和售票状态。
- **偏好设置**：用户填写偏好城市、预算范围、售票状态和艺人，系统将这些条件传给规则推荐函数。
- **推荐理由**：推荐卡片展示“当前可购”“讨论度高”“入场门槛友好”“符合偏好”等可解释理由，不显示预测概率。
- **页面内提醒**：只在看板中提示距离演出日期较近或即将开售的场次，不发送短信、邮件和实时推送。

#### 3.8.6 分阶段安排与边界

第一阶段优先完成地域地图、时间趋势、场次日历、票价分析、评论主题、艺人对比、导入预览和数据质量报告；第二阶段再完成收藏、对比、偏好和推荐理由。扩展功能不包括支付、真实购票、票房预测、复杂机器学习推荐、移动端 App、公开注册、实时消息推送和绕过访问限制的数据采集。

## 5 数据采集实施

### 5.1 数据来源原则

开题报告拟选择大麦网、猫眼演出等公开票务页面，以及哔哩哔哩等视频平台公开评论区作为数据来源。实施时先对候选页面进行可访问性检查：

- 页面是否不需要登录。
- 页面是否能够直接显示需要的字段。
- 页面是否允许低频访问和学习研究用途。
- 页面结构是否足够稳定。
- 是否可以保存来源 URL、访问时间和原始快照。

如果页面依赖复杂 JavaScript 动态加载、频繁出现验证码或无法稳定获取字段，不强行处理，改用已经获得的公开页面快照或 CSV 数据，并在项目记录中如实说明。

### 5.2 采集过程

1. 确定歌手和数据时间范围。
2. 记录来源名称、来源地址、采集日期和采集人。
3. 使用 `requests` 发送低频请求。
4. 使用 `BeautifulSoup` 按页面结构提取字段。
5. 对每个页面保存原始响应或整理后的原始 CSV。
6. 记录请求成功、解析失败和字段缺失情况。
7. 采集结束后再进入清洗模块，不在采集过程中随意修改原始文本。

### 5.3 采集异常处理

- 网络超时：记录 URL 和错误信息，允许下一条记录继续处理。
- 页面结构变化：保存原始页面，暂停该来源适配，不使用错误解析结果。
- 字段缺失：允许非关键字段为空，关键字段缺失时进入异常文件。
- 重复数据：在清洗阶段统一去重，不在原始快照中删除。
- 访问受限：停止继续请求，改用固定快照，不使用代理池或绕过措施。

- 地域、趋势、日历、票价、主题和艺人对比优先由现有五张核心表聚合计算，不为了少量演示数据盲目增加事实表。

- 城市经纬度和评论主题关键词属于项目配置数据，分别保存在 `data/dictionary/` 或配置模块中，并记录来源和更新时间；无法确认的坐标不写入数据库。

- 管理员内容编辑只修改可校正的基础字段，保留 `source_url`、`collected_at` 和原始 CSV，确保分析结果可以回溯。

## 7 数据清洗与文本分析实施

### 7.1 演唱会字段清洗

1. 使用字符串去除字段两端空格。
2. 使用统一日期格式转换演出时间。
3. 将“待售”“已售罄”“售票中”等文本统一为有限的状态值。
4. 用正则表达式和字符串切割提取票价数字。
5. 对存在多个价格的记录计算最低价和最高价。
6. 解析失败的票价不填写猜测值，保留原始票价文本。
7. 对重复记录保留一条，并输出去重前后的数量。

### 7.2 评论文本清洗

1. 删除 HTML 标签、无意义空白和明显控制字符。
2. 保留中文、英文、数字和有分析意义的常用符号。
3. 过滤空评论和只有表情的评论。
4. 对完全相同的评论进行去重。
5. 使用停用词表过滤“的”“了”“是”等高频无意义词。
6. 对“绝绝子”“神仙现场”等网络表达，根据实际数据补充自定义词典。

### 7.3 关键词和词频统计

使用中文分词工具对评论进行切分，过滤停用词后统计词频。输出内容包括关键词、出现次数和排名，并将结果保存到分析结果表或 JSON 文件，供词云图读取。

不同情感类别分别统计关键词，用于观察正面、负面和中性评论关注点的差别。由于本项目不进行人工标注验证，项目记录中只描述样本中的词频现象，不宣称该结果代表全部粉丝群体。

### 7.4 SnowNLP 情感分析

对每条评论计算 0 到 1 之间的情感分数，并按以下规则分类：

- 正面：分数大于或等于 0.6。
- 负面：分数小于或等于 0.4。
- 中性：分数大于 0.4 且小于 0.6。

项目可以根据演唱会评论中的网络表达增加少量自定义词典或修正规则，但需要记录修改内容和处理时间。情感分析只作为探索性统计，不在项目记录中报告未经人工标注验证的准确率、召回率或模型优越性。
### 7.5 评论主题规则

评论主题采用可解释的关键词集合，不引入复杂主题模型。初始主题和示例关键词如下：

| 主题 | 示例关键词 |
|---|---|
| 现场体验 | 现场、合唱、氛围、感动、歌单、返场 |
| 舞台音响 | 舞台、灯光、屏幕、音响、清晰、视线 |
| 交通场馆 | 场馆、交通、地铁、路线、停车、排队 |
| 票价购票 | 票价、价格、购票、票档、买票、开售 |
| 服务组织 | 工作人员、流程、入口、服务、安排、延迟 |

一条评论可以对应多个主题，但统计时需要记录总评论数和主题命中数，避免把主题数量误解为评论总数。每个主题分别计算评论量、点赞量和平均情绪分数；没有命中关键词的评论归入“其他”。关键词表放在 `data/dictionary/`，修改时记录版本和日期。

## 8 Flask 与 ECharts 实施

### 8.1 Flask 页面

Flask 负责：

- 返回首页和数据分析页面。
- 接收明星、城市和时间范围筛选条件。
- 查询 MySQL 中的基础数据和统计结果。
- 组织模板所需的列表、数字和图表数据。
- 对查询异常返回友好的提示信息。

### 8.2 登录与权限

使用 Flask-Login 管理管理员会话。未登录用户只能访问公开看板；导入数据、修改词典、触发分析任务和查看任务记录等操作必须先通过管理员登录。每个管理路由执行登录检查，退出后清除会话。

### 8.3 管理后台

后台页面包括登录页、数据导入页、任务操作页和运行记录页。后台调用 ORM 完成数据写入和查询，导入前显示文件名、字段和记录数，导入后显示成功和异常数量。

### 8.4 推荐查询

推荐路由接收城市、价格范围、时间范围和售票状态等条件，调用 `recommend.py` 的规则函数计算候选演唱会分数，再返回推荐列表。推荐结果与普通统计页面分开，便于测试规则是否生效。
页面层不直接执行爬虫和复杂文本分析。分析结果由脚本提前计算，页面只进行查询和展示。

### 8.5 页面布局

页面从上到下分为：

1. 页面标题和数据更新时间。
2. 筛选区域。
3. 演唱会总数、评论总数、城市数等基础统计。
4. 城市分布和票价统计图。
5. 评论趋势、地区分布和情感倾向图。
6. 关键词词云。
7. 演唱会信息列表和必要的评论摘要。
8. 管理员登录入口和管理后台入口。
9. 推荐演唱会列表。

### 8.6 图表数据

ECharts 图表使用 Flask 查询结果生成的 JSON 数据。每类图表至少包含标题、图例、坐标轴名称和数据单位。图表没有数据时显示“暂无数据”，不显示空白或错误图形。

### 8.7 综合扩展接口

公开看板在原有 `/api/overview` 和 `/api/recommendations` 基础上，规划以下接口能力：

| 接口 | 用途 | 权限 |
|---|---|---|
| `/api/overview` | 返回当前筛选下的指标、图表、场次、评论和推荐 | 公开 |
| `/api/analytics/map` | 返回城市坐标、场次数量和评论热度 | 公开 |
| `/api/analytics/trend` | 返回演出、评论和情绪的月度或周度趋势 | 公开 |
| `/api/analytics/calendar` | 返回日期和场次详情 | 公开 |
| `/api/analytics/prices` | 返回票价分布、城市价格比较和价格—热度数据 | 公开 |
| `/api/analytics/topics` | 返回评论主题数量、点赞量和主题情绪 | 公开 |
| `/api/analytics/artists` | 返回艺人维度的对比数据和样本提示 | 公开 |
| `/admin/api/import/preview` | 读取 CSV 并返回字段、示例、重复和异常报告 | 管理员 |
| `/admin/api/export/concerts` | 导出规范化演唱会数据 CSV | 管理员 |
| `/admin/api/jobs/<id>` | 查看单个任务的完整运行结果 | 管理员 |
| `/admin/api/concerts/<id>` | 修改或删除可校正的演唱会基础信息 | 管理员 |

接口统一返回 JSON；参数格式错误返回 400，未登录访问管理接口返回登录跳转或 401，服务器异常不返回数据库连接串和完整堆栈。扩展接口需要复用同一套筛选条件，保证图表、日历、列表和推荐结果不会出现口径不一致。

### 8.8 页面交互与状态

页面使用原生 JavaScript 管理轻量状态，不引入 React、Vue 或复杂状态管理框架：

1. 筛选表单提交后更新 URL 查询参数，并刷新指标、图表、日历、列表和推荐结果。
2. 地图、趋势、票价、主题和艺人对比图共享当前筛选条件，点击图表节点可以回填城市或艺人筛选（如点击城市柱状图自动应用该城市筛选）。
3. 顶部搜索条支持艺人/场次/城市/场馆关键字实时搜索，回车展示匹配结果，点击结果直接打开场次详情。
4. 点击场次卡片的名称或「查看详情」按钮，从右侧滑出**详情抽屉**：展示场次基本信息、票价明细、原页链接与观众评论；评论支持按页翻页（上一页/下一页），作为「演唱会信息列表和场次详情入口」的落地实现。
5. 场次卡片提供收藏和加入对比按钮，对比数量限制为 2–3 场，超出时显示提示。
6. 偏好面板的城市、预算、状态和艺人字段保存到 `localStorage`，刷新页面后可以恢复。
7. 推荐卡片同时显示分数、排序依据和文字理由；不显示“命中概率”等容易造成误解的字段。
8. 管理后台的导入流程分为“选择文件—预览校验—确认导入—查看报告”四步，禁止选择文件后无提示直接写库。

### 8.9 演唱会日历紧凑化

原演唱会日历按日期逐日排列，数据扩充到十万级后单月场次密集，页面被拉得很长，占空比过大。改为**紧凑月历热力图**：

1. 默认展示一个月份网格（行=星期，列=周一到周日），每个日期格只显示当天场次数，不显示场次明细。
2. 场次数按档位映射颜色深浅（0 场、1-3 场、4-10 场、10 场以上），形成热力效果，一眼看出哪几天最密集。
3. 点击日期格后，在日历下方显示该日场次列表，默认折叠，点击再展开，避免页面被长列表撑开。
4. 增加月份切换（上一月/下一月）和“回到本月”，限制日历整体高度为固定值，超出部分内部滚动。
5. 月份网格与场次列表共用 `/api/analytics/calendar` 同一数据源，保证数字一致。

这样日历区域的高度基本恒定，不再随数据量增加而无限变长。
## 9 定时分析实施

按照开题报告的设计，将采集与分析脚本分开：

1. 采集脚本写入新的原始 CSV。
2. 清洗脚本生成清洗后的 CSV。
3. 导入脚本写入 MySQL。
4. 分析脚本查询新增评论，执行分词、词频和情感分析。
5. 分析结果写入 `analysis_result`。
6. Flask 页面读取最新分析结果。
7. 扩展聚合模块生成地图、趋势、日历、票价、主题和艺人对比数据。
8. 管理后台保存导入报告和任务详情，供管理员复核。

本地开发阶段可以手动执行脚本；系统联调后使用 Windows 任务计划程序定期调用分析脚本。任务周期以实际机器环境为准，建议先使用每天一次，避免频繁访问公开页面。

## 10 实施步骤

### 第一步：确定数据字段和样例

先建立字段表，准备少量公开样例或固定 CSV，确认演唱会信息和评论信息能够对应。

### 第二步：完成采集模块

编写票务信息和评论信息的采集脚本，加入请求异常处理和原始数据保存功能。无法稳定采集的来源暂停，不影响后续使用快照继续开发。

### 第三步：完成清洗和 MySQL 导入

实现日期、价格、状态、评论文本清洗和去重，建立数据库表，导入清洗后的数据并检查字段值。

### 第四步：完成分析模块

实现中文分词、停用词过滤、词频统计、关键词提取和 SnowNLP 情感分类，保存统计结果。

### 第五步：完成登录、ORM、管理后台和推荐功能

使用 Flask-Login 完成管理员登录和权限校验，使用 Flask-SQLAlchemy 建立模型，完成 CSV 导入、任务触发和运行记录页面，再编写城市、价格、时间和热度规则推荐函数。

### 第六步：完成 Flask 页面和基础 ECharts 图表

先完成列表查询，再逐个增加城市、票价、评论趋势、地区、词云和情感图表，最后加入筛选条件，并验证图表与列表使用同一组筛选结果。

### 第七步：完成第一阶段综合扩展

增加地域地图、时间趋势、场次日历、票价分析、评论主题和艺人对比；实现 CSV 导入预览、字段校验、重复检测、异常票价提示、导入报告、任务详情、数据导出和最小化演唱会内容编辑。

### 第八步：完成第二阶段用户交互扩展

使用浏览器 `localStorage` 实现收藏、两到三场演唱会对比、偏好设置、推荐理由和页面内提醒。验证清除本地数据后公共看板仍可正常使用。

### 第九步：联调和整理材料

检查“采集/快照—清洗—数据库—ORM—分析—治理后台—推荐—用户交互—页面”的完整链路，记录真实运行结果，整理系统截图、测试表和验收材料。
### 第十步：补充公开快照并同步本地数据库

在基础种子数据之外，实际核验 9 个公开来源并新增 66 条演唱会记录。清洗后原始快照共 78 条，覆盖 57 位艺人和 12 个城市。Flask 非测试环境启动时自动导入 `data/raw/concerts.csv` 中尚未入库的记录，导入采用演唱会名称、城市、场馆和演出日期指纹去重；测试环境关闭自动加载，避免外部快照影响固定测试样本。

### 第十一步：切换为真实演唱会数据与多平台现场评论

按指导老师意见，数据主体改为**国内真实演唱会**，评论改为**与演出直接相关的观演评论**（不再使用与场次无关的歌曲评论）：

1. 使用 `scripts/export_damai_full.py` 从本地大麦爬虫库 `damai.db` 导出**全部有效演出**（排除「非演出商品」分类）：22618 场真实演出（演唱会 1062 / 音乐会 1741 / 音乐节 74 等分类，272 城市），保留分类、艺人、场次、城市、场馆、时间、票价、状态、来源地址与采集时间；前端支持按分类筛选，**默认只展示演唱会分类**（选择「全部」可查看全库）。
2. 艺人名清洗：将拼盘演出、歌曲名、舞台装置等噪音统一归入「群星」，保留可识别的真实艺人名（李荣浩、张韶涵、周华健、张震岳等），最终 307 位去重艺人。
3. 使用 `scripts/collect_social_comments.py` 从 B站公开评论 API（`x/v2/reply/main`，wbi 签名，无需登录）按艺人搜索"XX 演唱会"视频并抓取热评：1069 条与演唱会/现场直接相关的评论（如现场体验、舞台音响、票价、观演反馈），每条标注 `source_platform=bilibili` 与视频链接。
4. 网易云歌手热评 49060 条按歌手名关联到对应艺人（`comments_wyy_merged.csv`）；大麦全库场次真实评论 118412 条（`damai_full_comments.csv`）一并导入。
5. 全量导入由 `scripts/import_all_channels.py` 完成（场次 + 三渠道评论，幂等去重），`comment_info` 保留 `sentiment_score`（大麦自带 11.8 万条）与 `source_url` 来源标注。
6. 全部记录保留 `source_platform` / `source_type`、`source_url`、`collected_at`，论文可逐条复查来源。

### 第十二步：Redis 缓存与分析面板（九项 → 十四项）

十万级数据下分析接口需聚合大量评论，直接计算导致页面持续加载。引入 Redis 缓存后：

1. 新增 `app/cache.py` 缓存层：为 10 个分析/推荐接口提供 TTL 缓存（分析 300 秒、概览与推荐 120 秒），缓存键含筛选参数，管理后台变更数据后主动清空。
2. 采用 fail-open 降级：Redis 未启动或超时时自动回退无缓存计算，测试环境跳过缓存保证断言稳定。
3. 评论分析采样上限 3000 条、情感分入库持久化，控制单次聚合开销。
4. 分析中心升级为**十四项分析**：新增数据来源统计（07）、城市票价对比（08）、互动热度榜（09），艺人对比升级为综合热度 Top10（06）。
5. 实测：冷缓存约 1.2-2.2 秒，Redis 命中后全部接口 64-102 毫秒，首页恢复秒开。

## 11 测试方案

本项目采用普通本科毕业设计所需的功能测试和数据质量检查，不设计复杂性能实验。

### 11.1 数据采集测试

- 能否读取正常公开页面或样例快照。
- 页面字段缺失时是否能够继续处理并记录异常。
- 网络超时时是否输出错误信息。
- 是否保存来源地址和采集时间。
- 本次 9 个来源是否均返回 HTTP 200，来源日志是否写入 `data/raw/public_sources.csv`。
- 合并快照是否达到 78 条演唱会、57 位艺人和 12 个城市。

### 11.2 数据清洗测试

- 日期是否转换为统一格式。
- 多档票价能否得到最低价和最高价。
- 重复记录能否删除。
- 空评论和无效评论能否过滤。
- 清洗前后数据条数是否有记录。

### 11.3 数据库测试

- 五张核心表和 ORM 模型能否正常创建。
- 演唱会和评论记录能否插入和查询。
- 城市、票价和情感统计结果是否能够查询。
- 页面筛选条件是否能够正确传入查询。

### 11.4 页面测试

- 首页能否正常打开。
- 各类图表是否显示。
- 无数据时是否显示空状态。
- 按明星、城市和时间筛选后，列表和图表是否同步变化。
- 页面在常用浏览器中是否能够正常显示。

### 11.5 登录、后台与推荐测试

- 未登录用户访问管理页面时是否跳转到登录页。
- 正确管理员账号能否登录，错误密码是否被拒绝。
- 退出登录后是否不能继续访问管理页面。
- CSV 导入后成功条数和异常条数是否正确。
- ORM 查询和写入结果是否与数据库记录一致。
- 改变城市、价格和时间条件后，推荐列表是否发生变化。
- 推荐结果是否按照预设规则排序。

### 11.6 扩展分析和后台治理测试

- 城市地图是否只显示有可靠坐标的城市，缺失坐标时是否保留统计结果并提示。
- 时间趋势是否能够按月或按周返回演出量、评论量和情绪均值。
- 场次日历点击日期后是否显示当天场次详情。
- 票价区间、城市价格比较和价格—热度数据是否与基础记录一致。
- 评论主题是否按照关键词规则分类，主题情绪和点赞量是否可查询。

## 12 风险与处理

| 风险 | 处理方式 |
|---|---|
| 页面结构变化 | 保存原始快照，暂停该适配器并修改解析规则 |
| 动态页面无法直接解析 | 不绕过限制，使用合规快照或用户提供的公开数据文件 |
| 票价文本复杂 | 保留原始文本，解析失败时记录异常 |
| 评论文本包含网络用语 | 使用停用词表和少量自定义词典，并在项目记录中说明局限 |
| 用户地区字段缺失 | 保存为空并统计缺失情况，不进行猜测 |
| SnowNLP 结果与人工感受不完全一致 | 只作定性分析，不报告未经验证的模型准确率 |
| 数据量不足 | 先保证完整主流程，再在时间允许时扩展歌手和评论范围 |
| 登录配置错误 | 使用密码哈希和环境变量，首次运行时初始化管理员账号 |
| ORM 查询与原生数据不一致 | 使用模型字段与表字段一一对应，并用数据库测试核对 |
| 推荐结果过于简单 | 明确采用规则推荐，展示规则和权重，不宣称个性化准确性 |
| 地图坐标不准确 | 只使用可靠的城市级坐标，缺失或无法确认时只显示城市统计 |
| 主题分类重叠 | 允许一条评论命中多个主题，同时记录主题命中规则和总评论数 |
| 多维图表口径不一致 | 所有扩展接口复用统一筛选参数，并用同一批聚合结果生成页面 |
| 导入异常未被发现 | 导入前预览和校验，导入后生成新增、重复、异常和成功报告 |
| 内容编辑破坏来源依据 | 只允许修改基础展示字段，保留原始 CSV、来源地址和采集时间 |
| 本地收藏数据丢失 | 明确收藏和偏好只保存在浏览器，公共数据和推荐功能不依赖本地状态 |
| 扩展范围过大 | 按两个阶段实施，优先完成分析中心与后台治理，再完成轻量用户交互 |
